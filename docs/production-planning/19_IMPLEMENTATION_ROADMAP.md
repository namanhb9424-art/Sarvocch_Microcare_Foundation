# Phased implementation roadmap

Priorities mean P0 is required before real business data, P1 is needed for approved core workflows, P2 expands operations, and P3 is optional refinement. Sequence is dependency-driven; planning ranges are in `23_REMAINING_EFFORT_ESTIMATE.md`. The owner selected the existing microfinance product; manufacturing scope is excluded. This roadmap is a live implementation tracker: phases 0–4 have source changes in this worktree, while the remaining gates below still require implementation or external verification.

Sign-in now performs equivalent PBKDF2 work for valid-length attempts with unknown usernames, locked accounts or unsupported stored verifiers to reduce username timing disclosure. This does not establish constant-time behavior or replace device-level verification.

Do not treat source implementation or the debug APK as production approval. Continue with the unfinished MFI and data-integrity phases and the external release gates.

Schema v25 snapshots product name, repayment method, amount and tenure limits, and configured fee on new loan applications. Approval and disbursement use those saved terms, so later catalogue edits do not silently change an application in progress. Older applications are backfilled from their linked product during migration. Schema v26 adds a duplicate-safe partial unique index for pending attendance corrections by user and day. Attendance corrections recheck actor, target and request state in the write transaction; punch-out rechecks the active account, and punch-in reads the active branch geofence inside its transaction. Schema v27 revokes exact bundled demo identities without deleting their referenced records and restores initial setup availability when needed. Schema v28 clears pending collection-task loan links when they are inconsistent or ambiguous across multiple active loans, so the officer must select the loan and due installment. Installment payment validates against stored paise, writes the payment and paid marker atomically, and records amount in paise in its audit event; loan schedule reconciliation prefers integer paise columns. Schema v29 adds salary-in-paise storage. Schema v30 adds paise columns for all application income/expense components, group and center amounts, requested amount and derived cashflow totals. It backfills only exactly representable legacy values, reports invalid rows for review, rejects mismatched writes, and uses integer paise for the application affordability threshold. These migrations and transaction paths need sanitized-fixture runtime verification.

## Likely Flutter areas to touch

Current source areas include `lib/main.dart`, `lib/data/database_helper.dart`, `lib/models/`, `lib/providers/`, `lib/screens/`, `lib/services/`, `assets/`, platform wrappers and `test/`. The Flask source includes `app.py`, templates, static assets and deployment files. Exact file impact should be refined after domain/scope decision; this list is not an authorization to change these files during discovery.

## Definition of done per phase

Every phase has reviewed requirements, transaction boundaries, migration impact, accessibility/security review, test evidence, operational notes and product-owner sign-off. Block downstream phases on unresolved financial reconciliation, unsafe authorization, destructive migration or unapproved MFI policy.
